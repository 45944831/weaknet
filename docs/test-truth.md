# 测试期望的来源

> 配套检查器：`tests/_t_expect.py`（本地可跑，CI 必跑）
> 配套用例：`tests/test_unit_expect_truth.py`
> 首次盘点：2026-11-27（第五件）

## 一、为什么需要这份清单

测试全绿只能证明「实现与期望一致」，不能证明「实现是对的」。区别在于期望从哪来：

- 期望来自 **spec / RFC / 平台文档 / 实测** → 实现错了，测试会红；
- 期望来自 **被测实现本身** → 改实现时把期望一起改，测试永远绿。

后者就是「抄实现的期望」。它不一定写错，但**没有发现错误的能力**。本轮把它逐类盘出来，并把「这个值谁保证」写进代码，让评审问得出这句话。

## 二、盘出来的五类

统计口径：34 个 pytest 模块、1190 条断言（第十四轮补变异缺口后从 1071 涨到 1138，再补 USB 孤儿映射 5 条用例到 1159，补 3 条已知边界用例到 1181；第十五轮修 WinINET 删 `AutoDetect` 导致系统代理接管失败，新增 2 条假注册表用例，另外几处测试工具修正补断言，合计 1190；镜像组 17 → 18，新增的是 `_down_head` 幂等不变量）。

| 类 | 规模 | 典型写法 | 能发现"值错了"吗 | 处置 |
|---|---|---|---|---|
| A 常量镜像 | 17 组 | `assert body["spec_hash"] == W.SPEC_HASH` | 不能；由锚点用例负责 | 逐组登记理由 |
| B 公式镜像 | 1 组 | `step_seconds(x) == STEP_MAX_MINUTES * 60 + ...` | **不能，且没有锚点** | 已改成字面量 |
| C 恒真断言 | 0 条 | `assert x == x` | 不能 | 规则永久拦截 |
| D 文案快照 | 292 处（27%） | `assert "下行延迟" in text` | 不适用（措辞契约） | 标注为快照，不当正确性证据 |
| E 现状契约 | 1 处 | `drains == 3`（每块都 drain） | 不能 | 登记依据（A/B 实测） |

### A. 常量镜像（17 组）

断言一侧是被测符号（`W.常量` 或 `W.函数()`），另一侧是被测输出。这类断言只能证明「值传到了」，不能证明「值对」。逐组登记后，理由分四种：

| 理由 | 组数 | 例子 | 值本身由谁保证 |
|---|---|---|---|
| 管线回显 | 5 | `body["spec_hash"] == W.SPEC_HASH` | `test_unit_spec` 对 spec 文件哈希 |
| 规格真值 | 6 | `W.PROF_LIMITS == {p["key"]: int(p["max"]) ...}` | `spec/spec.json` |
| 跨端对拍 | 3 | `scenes == W.DEFAULT_SCENES`（Java 生成值 vs Python） | `gen_spec.py --check` 保证同源 |
| 产品决策 / 不变量 | 3 | `W._share_clean(label) == label` | 幂等性本身 |

### B. 公式镜像（1 组，已修）

```python
# 修前：上限一改，两边一起变
assert W.step_seconds({"minutes": 9999, "seconds": 9999}) == \
    W.STEP_MAX_MINUTES * 60 + W.STEP_MAX_SECONDS
# 修后：600 分 59 秒 → 36059，改上限必须有人来解释
assert W.step_seconds({"minutes": 9999, "seconds": 9999}) == 36059
```

### D. 文案快照（292 处）

报告与 GUI 的措辞断言，占全部断言的 27%。它们的价值是**防止文案被无意改掉**，不是证明数字算对了。已把 `test_report_gen.py`、`test_gui_state.py`、`test_gui_text.py`、`test_unit_text_layout.py` 的来源标为「文案快照」，与「正确性」区分开。

报告里的数字断言已单独核过：`150 ms` / `8000 kbps` / `1.00 MB` 都来自测试自己设定的 payload，不是从 `report_gen.py` 抄的。

## 三、检查器

`tests/_t_expect.py` 做六件事：

| 规则 | 检查内容 | 失败示例 |
|---|---|---|
| X1 覆盖 | 每个 `tests/test_*.py` 都在 `SOURCES` 登记来源 | 新增测试文件没写来源 |
| X2 可解析 | 来源是真实文件、`RFC NNNN`，或已定义标签 | `docs/不存在的.md` |
| X3 恒真 | 断言两侧语法完全相同 | `assert W.NAME_MAX == W.NAME_MAX` |
| X4 镜像 | 未登记的常量/函数镜像 | `assert body["n"] == W.NAME_MAX` |
| X5 过期 | 登记表里的条目代码中已不存在 | 删了断言没删登记 |
| X6 公式 | 实现常量参与乘除（抄公式） | `== W.MAX * 60` |

来源标签共九种：`规格真值`、`协议真值`、`平台真值`、`实测真值`、`跨端对拍`、`产品决策`、`文案快照`、`管线回显`、`现状契约`。

**登记不是豁免。** 登记项的值必须能回答「谁保证它」；只能答「实现就是这么写的」，就不该登记，应该改成字面量或从 spec 推导。

## 四、当前来源分布（诚实版）

| 来源 | 模块引用次数 |
|---|---|
| 产品决策 | 21 |
| `spec/spec.json` | 8 |
| 平台真值（SDK / Java / WinINET） | 6 |
| 协议真值（RFC） | 6 |
| 文案快照 | 5 |
| 实测真值 | 4 |
| 跨端对拍 | 2 |

「产品决策」占大头是事实：大部分界面行为的上限、默认值、措辞本来就是人为定的。它的含义是「改动需要人确认」，不是「已经验证过」。

## 五、抓不到什么（比能抓什么更重要）

1. **照着输出抄的字面量**。`scene_sequence` 那次：实现把 `A→B→A` 去重成 `A→B`，测试就把 `["A","B"]` 写成期望。两侧都是字面量，任何静态规则都判不出来——只能靠「期望必须先于实现写下」的流程。
2. **文案快照里的语义错误**。断言「报告里有『本次所有参数均为默认值』」不能发现这句话在参数非默认时也出现。
3. **两端一起错**。跨端对拍只能证明一致，不能证明正确；`note_wrap_golden.txt` 以桌面实现为基准，两端同时错时它也绿。
4. **没写出来的断言**。检查器只看已存在的断言；缺失的覆盖它看不见。

对应的办法不是加规则，而是换手段：真机抓包、协议栈对照、变异测试。静态检查在第 6 轮左右就饱和了，这一点在第 8 轮的复盘里已经写过。

## 六、怎么用

```bash
# 本地检查（退出码非 0 即有未登记项）
python tests/_t_expect.py

# 打印每个模块的来源与断言数
python tests/_t_expect.py --list
```

新增测试文件时：先在 `SOURCES` 里写清真值来源，再写测试。CI 的 `unit-tests` job 会在 pytest 之前跑一遍，`test_unit_expect_truth.py` 另有一组用例证明每条规则真的会红。

改期望值时，先问三句话：

1. 这个值的真值来源是什么？变了没有？
2. 如果来源没变，是不是实现错了？
3. 如果来源变了，改的是 spec 还是产品决策？文档跟上了没有？
