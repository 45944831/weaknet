# 弱网模拟精度声明与边界

> 本文件回答一个问题：**WeakNet 能模拟什么、不能模拟什么、数字能信到什么程度。**
> 任何把 WeakNet 的「丢包」「延迟」当成内核级链路损伤的结论都是错的，这里把差别写清楚。

## 1. 模拟发生在哪一层

| 方案 | 实现位置 | 损伤对象 | 典型工具 |
|---|---|---|---|
| **WeakNet（本项目）** | 应用层代理（Windows）+ 用户态 TUN 隧道（Android） | **本进程转发出去的数据块** | — |
| 内核 qdisc | Linux `tc` / `netem` / `tbf` | 内核协议栈里的**每个 IP 包** | tc、netem |
| 系统网络栈钩子 | Windows WFP/WinDivert | 每个包 | Clumsy |
| 物理链路 | 损伤仪 | 电信号 | Spirent 等 |

**直接后果**：WeakNet 看到的「包」是它自己转发时的一次读写块（Windows 侧 64KB、Android 侧按 MSS），
不是 TCP 段，更不是 IP 包。因此所有参数的**粒度**都受这一层限制，不能与 netem 直接等价。

## 2. 每个参数的真实语义

| 参数 | 实现 | 语义与偏差 |
|---|---|---|
| 带宽 | 全局令牌桶，**每个字节都过闸**（上行/下行各一个桶，所有连接共享） | 速率单位 1 kbps = 1024 bit/s。并发连接**分摊**同一个桶，不叠加（这是刻意的：模拟一条链路）。低于约 64KB/RTT 时受块大小限制，实际速率会明显低于设定值 |
| 延迟 | 每块数据按到期时间投递（`DelayLine`），**不是**只延迟建连 | 生效于每个数据块，所以 keep-alive / WebSocket / 视频流同样吃延迟。设定值是「单程」，客户端观测 RTT ≈ 上行 + 下行 |
| 抖动 | ±jitter，同一方向的到期时间**单调不减** | 这是保序钳制：不会出现后发先至。代价是抖动分布被截断为「只会推后」，观测到的抖动略小于设定值 |
| 丢包 | **表现为一段传输停顿**（`stall_ms`），不是真的丢包 | TCP 不会因此触发重传，只会因为等不到 ACK 而受限；对 UDP 则完全不丢包。这是与 netem 最大的语义差异 |
| 断连 | 立即 RST/FIN 掐断整条连接 | 与真实断连接近，但不会有「半开连接」状态 |
| 黑洞 | 建连后不响应，客户端超时 | 用于验证超时/重试逻辑，不产生 ICMP unreachable |
| 拒连 | 立即失败（HTTP 502 / RST） | 对应「服务器拒绝」，不是「网络不可达」 |
| DNS 故障 | 对 53 端口的 UDP 查询直接丢弃 | 只影响走 UDP 53 的查询；DoH/DoT 不受影响 |
| 并发 | 全局桶 + 每连接独立状态机 | 8 并发总**上限** = 设定带宽 × 1.15（验收项，防超发）；这是上限不是实测值。实测 8 并发 @8000 kbps 中位 **7,939 kbps（0.99× 设定值）**，与单流 7,988 kbps（1.00×）一致 —— 并发连接**分摊**同一个桶，总量不叠加也不打折，见 §4.1 表 1 |

## 3. 已知偏差（按重要性）

1. **丢包不是丢包**：表现为停顿，因此「丢包率 5%」在吞吐上的表现接近「每 20 块卡一次」，
   而不是「每 20 个包重传一次」。要测真实重传行为必须用 tc/netem。
2. **延迟粒度是块**：一块 64KB 在 1Mbps 下本身就要 0.5s，此时再叠加 200ms 延迟，
   端到端时间不会简单相加。
3. **带宽低于块大小时失真**：设定 8kbps（1KB/s）而块是 64KB 时，单块要 64s，
   表现为「长时间不动然后一次性到达」。
4. **UDP 队列满会丢**：UDP 没有拥塞控制，`DelayLine` 满（256KB）时按真实路由器行为丢包并计数。
5. **Android 侧 MSS 与 MTU 耦合**：`VpnNetService.TUN_MTU` 是单一真值，MSS 上限随之派生。
   只改 MTU 不改 MSS 不会带来任何吞吐收益（当前实现已联动，改一处即可）。
6. **低速档偏差是非线性的**（2026-11-13 实测，见 §4.1 表 2）：设定 500 kbps 实测中位
   **461 kbps（−7.9%）**，1000 kbps 实测 973（**−2.7%**），4000 实测 3,993（−0.2%），
   8000 实测 7,989（−0.1%），20000 实测 20,003（+0.0%），50000 实测 49,990（−0.0%）。
   低速时 64KB 块粒度与令牌桶补充节奏主导，偏差不再是固定百分比；**±15% 的验收区间
   在 500 kbps 档成立（−7.9%），但余量最小**，再往下（<500 kbps）不承诺。
7. **外部真值的统计口径必须是接收端**（2026-11-13 修正，重要）：iperf3 的 `sum_sent`
   是**客户端本地**的发送计数，多流共享瓶颈时该计数系统性少计最多 36%（−P 8 时
   6,708 kbps，而服务端真正收到 8,009 kbps，代理侧自计 8,083 kbps）。拿它当限速精度
   结论，会凭空造出「8 并发限速低 36%」的**假缺陷**。口径由
   `tests/perf/test_iperf_extract.py` 单测锁死，详见 §4.2。
8. **测量窗口会改变偏差读数**：短窗口包含更多慢启动与队列建立阶段。本轮起
   **8 场景与三张曲线统一为 7 次 × 20 s、`-O 3`**，同一批内窗口一致可横向比较；
   但跨批次比较仍须核对 `context.inputs`（窗口、`-O`、重复次数）。
9. **多并发的流间速率不均**：−P 8 时 8 条流各自的接收速率在 665–1,331 kbps 之间
   （理想值 1000），约 1.9 倍差距。这是 TCP 自己在共享瓶颈上的公平性结果，
   不是 WeakNet 的调度缺陷；但**单看某一条流的速率会低估总吞吐**，
   引用并发档数据必须用「各流之和」。
10. **发送端计数的误差方向不定，幅度可达 ±46%**（2026-11-14 补充证据）：同一版代码
   在 8000 kbps、−P 8 下，`sum_sent` 三次测量分别是 **−46%**（4,095 vs 7,938）、
   **+9.5%**（8,836 vs 8,067）、**−38.7%**（4,915 vs 8,007）。所以「发送端偏低」
   不能当作稳定的修正系数，唯一正确做法是**根本不拿它下结论**——它只作为归档里的
   口径旁证。接收端与引擎自计在同样三次里始终吻合在 ±4% 内，见 §4.5。
11. **短样本超发是「时间额度」，不是「固定字节额度」**（2026-11-14 修正旧结论）：
   令牌桶空闲后会攒满 `cap() = rate × BURST_SEC`，放行的是一段时间的流量。
   因此超发比例 ≈ `BURST_SEC / 理想时长`，**与速率成正比、与样本大小成反比**。
   旧报告写的「固定 0.42 MB 免费额度」只在单一速率下成立，换速率即失效；
   实测与模型见 §4.6。Windows `BURST_SEC=0.25`；Android 原为 `rate`（1.0 s，两端差 4 倍），
   **2026-11-14 已对齐为 0.25 s**（`Pipe.Bucket.BURST_SEC`，构造起始为空，与 Windows 同源），
   真机 A/B：1 MB@4000 冷测超发 **1.463× → 1.014×**（详见 verification.md）。

## 4. 怎么校准

不要用「感觉」，用外部真值。仓库里的 `tools/perf_iperf.py` 把整条链路固化成脚本：
起 iperf3 服务端、起 WeakNet 进程内引擎、用 CONNECT 隧道把裸 TCP 流送进代理，
逐档跑 `-J` 并归档中位数 / p95。二进制本身不放进仓库（体积大、平台相关），
用 `--iperf3` 或 `WN_IPERF3` 指定。

```bash
# 1) 链路自检（2 次 × 3s，先确认服务端/隧道/引擎都通）
py -3.10-64 tools/perf_iperf.py --quick

# 2) 正式外部真值：7 次 × 20s，直连 P1/P4/P8/UDP + 经 WeakNet P1/P4/P8/-R
py -3.10-64 tools/perf_iperf.py

# 3) 偏差曲线（P2-1）：带宽 6 档 + 高延迟×低带宽 4 档 + 丢包×带宽 3 档
py -3.10-64 tools/perf_iperf.py --curve
py -3.10-64 tools/perf_iperf.py --curve-latency --curve-loss

# 等价的手工命令矩阵（脚本内部就是这些）
iperf3 -c <host> -J -t 20 -O 3 -P 1 > direct_p1.json
iperf3 -c <host> -J -t 20 -O 3 -P 8 > direct_p8.json
iperf3 -c <host> -J -t 20 -O 3 -P 1 -R > via_weaknet_rev.json   # 反向：下行过闸
iperf3 -c <host> -J -t 20 -O 3 -u -b 10M > udp.json              # 直连 UDP 抖动/丢包

# 4) Linux 内核级参照（本项目**不等价**，只用于交叉校准）
tc qdisc add dev eth0 root netem delay 200ms 50ms loss 5%
```

**三条必须写清楚的限制**：

1. **经 WeakNet 的 UDP 测不了，不是脚本的缺陷。** Windows 侧是 TCP 应用层代理，
   CONNECT 隧道只转发裸 TCP 字节流；iperf3 `-u` 的 UDP 数据报在控制连接之外另发，
   不会进隧道（实测两轮都 timeout）。所以 UDP 抖动 / 丢包只做**直连真值**，
   Android 侧 UDP 承载在 VpnService 的 TUN 里，需要设备端 iperf3 客户端才能测。
2. **单位口径不同**：iperf3 的 `bits_per_second` 是 SI（1000 进制），本项目的
   kbps 是 1024 bit/s。脚本同时记录原始 bps 与换算后的 `kbps_1024`，
   不要把 2.4% 的单位差当成产品偏差。
3. **统计口径取接收端**：`sum_received` 才是「真正抵达链路终点」的字节；
   `sum_sent`（客户端本地计数）在多流共享瓶颈时会少计最多 36%，拿它当限速精度
   结论会造出假缺陷。详见 §4.2。

判定口径：**≥7 次取中位数与 p95**，先跑一次不带 profiler 的基线，再对比；
同机同版本、一次只改一个变量。单次结果不足以支撑任何结论 ——
项目里的 `tun_ab.json` 就是两轮结论完全相反的反例。

**内外交叉验证**（2026-11-14 统一单位后重算）：进程内门禁 `bw_8000_kbps` 中位
**8,258 kbps** 与 iperf3 单流外部真值 7,988 kbps 相差 **3.4%**；**8 并发门禁
7,946 kbps 与外部 `weaknet_p8` 8,007 kbps 相差 0.8%**。两套完全独立的测量
（HTTP 测试客户端 vs iperf3 + CONNECT 隧道）高度吻合，说明测量体系自洽。

> **但这 3.4% 里有一半以上不是「差异」，是门禁样本自身的结构偏移**（2026-11-14 补注）：
> `bw_8000_kbps` 每次只下 **2 MB = 32 个 64 KB 块**，而令牌桶空闲攒下的额度会让
> **第一个块免费**。于是 `8,258 = 8,000 × 32/31` —— 中位数精确等于这个代数式
> （12 位小数吻合），说明它不是「限速超发 3.2%」，而是「32 个块里收了 31 个的钱」。
> 扣掉这个偏移：`8,258 × 31/32 = 8,000.0`，与外部真值 7,988 只差 **0.15%**。
> 所以门禁数字**不能直接当限速精度引用**，它只在「同一窗口、同一块数」的纵向比较里有效；
> 短样本的通用规律见 §4.6。

> **口径修正记录**：本节曾写「门禁 8,454 kbps，与外部真值相差 5.8%」。
> 8,454 是**旧的 SI 口径**（`字节×8/1000`），而产品声明的 1 kbps = 1024 bit/s；
> 同一个测量按 1024 换算就是 8,258。旧写法把 **2.4% 的单位差混进了「内外差异」**，
> 让测量体系看起来比实际更不自洽。2026-11-14 门禁已改用 1024（`test_perf.py`），
> 基线随之重录为 8,258 kbps。

**结论（与上一版相反）**：限速精度在 500–50,000 kbps 全档、单流与 1/4/8 并发、
单向与反向、带延迟与带丢包的组合下**全部落在 ±8% 以内**，绝大多数 ±3% 以内。
上一版把「8 并发低 36%」列为不达标项，那是统计口径造成的假缺陷。

**三条使用限制**：

1. `weaknet_udp` 场景**不存在**：Windows 侧是 TCP 应用层代理，UDP 数据报不经 CONNECT
   隧道（实测两轮 timeout）。UDP 抖动/丢包只有直连真值；Android 侧 UDP 在
   VpnService TUN 里，需要设备端 iperf3 才能测（当前设备未安装）。
2. `direct_*` 是本机回环，只能证明「外部链路不是瓶颈」，不能当作 WAN 参考值。
   要与内核级损伤对照仍需 Linux `tc netem`（§4 命令矩阵）。
3. 引用并发档数据必须用「各流之和」而不是单条流的速率（见 §3 第 9 条）。

### 4.2 一次「把假缺陷当成真缺陷」的记录（2026-11-13）

上一版文档曾写「8 并发 @8000 kbps 只有 4,609 kbps（−42.4%），属于产品真实行为，
明确不达标」。**该结论是错的**，根因在测量工具：

`tools/perf_iperf.py` 的 `_extract()` 原先优先取 iperf3 的 `sum_sent`（**客户端本地**
发送计数）。多流共享同一个瓶颈时，客户端几乎全程阻塞在 `send()` 里，本地计数
系统性落后于真正被对端收到的字节 —— 极端时个别流 `sender.bytes` = 0 而
`receiver.bytes` = 2.7 MB。

定位方法是**把链路拆成三段各测各的，并用两个互相独立的计数器对账**：

| 段 | 链路 | iperf3 上报 | 引擎 `bytes_up` |
|---|---|---:|---:|
| A | 直连（机器本底） | 45,110,878 kbps | — |
| B | 过隧道+代理，不限速 | 2,813,046 kbps | 2,753,207 kbps |
| C | 过隧道+代理，限速 8000 kbps，−P 8 | 5,275 / 3,636 kbps | **8,083 / 7,935 kbps** |

C 段里引擎侧稳定搬运 8000 kbps（与 −P 1/4 完全一致），整形逻辑没少给字节；
服务端接收侧同样落在 8000 kbps。三方一致、只有客户端本地计数偏低。

**处置**：`_extract()` 改以接收端 `sum_received` 为主口径，发送端数字并列留存
（`median_sender_kbps_1024` / `median_sender_receiver_gap_pct`），归档可自证；
新增 `tests/perf/test_iperf_extract.py` 5 条单测钉死口径。

**教训**：一个「看起来像产品的严重缺陷」的信号，最该先被质疑的是**测量工具本身**。
本项目此前已有 `tun_ab.json`「两轮结论完全相反」的先例；这次差点又踩一次，
区别在于这次做了「两个独立计数器对账 + 逐流明细」而不是靠反复调产品参数。

### 4.3 定时器分辨率与睡眠粒度（2026-11-13 第六轮修正）

Python 3.10 在 Windows 上，`asyncio.sleep` / `wait_for` 的实际粒度是系统定时器
分辨率 **15.625 ms**（64 Hz）；3.11 起 `time.sleep` 已换高精度定时器
（GH-89592），本项目钉在 3.10 只能用 `winmm.timeBeginPeriod(1)` 补。
本机实测（30 次取中位，serve() 启动时自动调用，`WN_TIMER_RES=0` 可关）：

| 请求睡眠 | 修正前实际 | 修正后实际 |
|---|---:|---:|
| 1 ms | 15.74 ms | **1.14 ms** |
| 5 ms | 15.58 ms | **6.46 ms** |
| 16 ms | 31.18 ms | **17.48 ms** |
| 64 ms | 78.26 ms | **65.56 ms** |

对精度的影响（门禁 4 项 × 7 次，同机同批）：

- 带宽门禁中位 8,389 → **8,192 kbps**，对 8000 设定值的偏差从 +4.9% 收敛到
  **+2.4%**（节奏睡眠被量化到 15.6ms 时，令牌桶每轮多攒出可突发额度）；
- RTT 门禁 p95 与中位相等（406~407 ms，偏差 +1.5%），修正前 p95 波动到 422 ms；
- 停止后放行积压 219~266 → **203 ms**。
- 64MB 直连 A/B（`WN_TIMER_RES=0/1` 交替 5 对，n=3 中位逐对比值 0.970~1.124、
  中位 **1.001×**）：直连快路径无回归，sha256 全一致。

代价：1ms 定时器中断略增功耗（Win10 2004+ 起该请求**只影响本进程**）；
省电优先时设 `WN_TIMER_RES=0` 即回旧粒度。

随本轮一起落地的两个参数（对精度影响小，一并记录）：

- **accept 侧 TCP_NODELAY**：asyncio 的 `_set_nodelay()` 只认 `sock.proto ==
  IPPROTO_TCP`，出站套接字 proto=6 满足、accept 进来的 proto 被推断为 0 不满足
  —— 实测 `start_server` 接受侧 NODELAY=0。入口 handler 统一补设；影响的是
  小请求-小响应的交互路径（Nagle+延迟 ACK 可多等 40~200ms），对 64KB 大块
  转发无影响。
- **GC 阈值**：`gc.collect(2) → gc.freeze() → set_threshold(20000, 50, 100)`
  （serve() 启动时一次），消除对象流转密集下的 gen0 高频回收停顿；
  不做「关 GC」的激进方案（asyncio 流确实产生循环引用）。

### 4.4 Android 端屏幕适配参数（2026-11-13 第六轮）

Android 端 UI 全部由 Java 代码构建（无布局 XML），适配收口在 `Ui.java`：

- **断点**：WindowSizeClass 官方值 600/840dp。2025-2026 主流手机竖屏全部
  <480dp（含「1.5K」档），≥600dp 的只有平板（Tab S11 ~914dp、Pad 7 ~777dp）
  与折叠屏内屏（Z Fold 7 ~832dp、Pixel 10 Pro Fold ~820dp）。
- **网格列数**：`Ui.columns` 现算——手机 3 列（旧行为）、Medium 5 列、
  Expanded 6 列；场景与组合两处网格同口径，每次重画时刷新（折叠开合跨断点自动跟上）。
- **弹层宽度**：`Ui.sheetWindowWidth/sheetContentWidth`——紧凑屏保持旧行为
  （窗口全宽、卡片屏宽-margin），≥600dp 封顶 560dp（Material 2/3 规范）居中。
- **方向**：`MainActivity.applyOrientationPolicy`——sw<600dp 锁竖版（旧行为），
  ≥600dp 放开（Android 12L+ 对大屏方向锁定会 letterbox（质量红线），16/17

- **悬浮窗**：`Ui.clampOverlay` 把拖动/初始/轮询三个点的位置钳进

  故 API 28+ 显式 `LAYOUT_IN_DISPLAY_CUTOUT_MODE_ALWAYS` + 钳制双保险。
- **矩阵**：推荐真机验证矩阵与来源见第六轮报告
  `_性能参数与屏幕适配落地报告_2026-11-13.md`。

### 4.5 采集质量自证：让数据自己回答「这批能不能用」（2026-11-14）

前面的口径修正解决了「取错字段」，但没解决「**这批样本本身可信吗**」。
两次事故都是这个问题的变体：

1. 一次重测同时跑了 Java 编译与 pytest，`direct_p1` 从 16 M 掉到 13.5 M。
   归档里除了数字什么都没有，只能靠人回忆判定作废。
2. `−P 8` 的样本里混着 2,459 / 2,918 kbps 的离群轮，但**中位数与 p95 与稳定批
   完全相同**（都是 7,946），差点被当成达标写进文档。

现在采集器每轮都记环境，并把「能不能用」写成结构化结论。

**新增的轮级字段**（`rounds[]`，每轮一条）：

| 字段 | 含义 | 为什么必须采 |
|---|---|---|
| `cpu_busy_pct` | 该轮系统 CPU 平均忙率（`GetSystemTimes`，纯 ctypes 零依赖） | 唯一无法事后补算的维度；有它才能识别「这一轮被别的进程抢了」 |
| `engine_kbps` | 代理层自计吞吐（`/api/status` 的 `bytes_up/down` 差值） | 与 iperf3 完全独立的**第三个**计数器 |
| `window_s` / `elapsed_s` | iperf3 自报有效窗口 / 进程墙钟 | 两者差 2~4 s（含 `-O` 预热），混用会凭空多算 70% |
| `mem_avail_mb` | 采集时可用物理内存 | 排除「内存压力导致的抖动」 |

**新增的聚合字段**：

| 字段 | 判据 | 用途 |
|---|---|---|
| `cv_pct` | `stdev / median × 100` | **>5% 即禁止引用中位数**；双峰批的 cv 是 36%，稳定批是 0.1% |
| `stdev` / `mad` / `iqr` | 标准差 / 中位绝对偏差 / 四分位距 | 小样本下 `mad`/`iqr` 比 `stdev` 抗离群 |
| `p95_is_extreme` | `n < 20` 时为 true | 最近秩法下 p95 恒等于 max，不标注就是假的分位 |
| `quality.usable` | `cv ≤ 5%` 且无污染轮 | 数据自己的结论，不是人的判断 |
| `quality.suspect_rounds` | CPU > 中位 + 3×MAD **且** > 15% **且** 高出中位 ≥15pp | 定位到具体哪一轮被抢占 |
| `quality.engine_crosscheck_ok` | 引擎 vs 接收端落在 −5%~+12% | 两套独立计数器对不上，说明链路串了或口径被改坏 |

`p95_is_extreme` 与 `suspect_rounds` 的三重判据都是必要的：高速档
（`direct_p8`）本身就把 CPU 打到 96%，只看「中位 + 3×MAD」会把 97% 的正常轮
误判成污染；只看绝对阈值又会把空闲批次 1%→3% 的抖动放大成异常。

**实测三方对账**（2026-11-14 14:05，8000 kbps，7 次 × 20 s、`-O 3`、轮间冷却 1.5 s）：

| 场景 | iperf3 接收端 | 引擎自计 | 差 | `sum_sent` | 差 |
|---|---:|---:|---:|---:|---:|
| `weaknet_p1` | 7,988 | 8,016 | **+0.4%** | 8,293 | +3.2% |
| `weaknet_p4` | 7,987 | 8,076 | **+1.1%** | 8,602 | +7.0% |
| `weaknet_p8` | 8,007 | 8,121 | **+1.4%** | 4,915 | **−38.7%** |

接收端与引擎两套独立计数器吻合在 ±1.4%，而 `sum_sent` 的偏差在同一批里从 −38.7%
跳到 +7.0%（见 §3 第 10 条）。**这就是「只信接收端」的实证依据**。

同批的 `cv_pct`：经代理四档 **0.03% ~ 0.73%**，全部 `quality.usable = true`。

**判据的一处修正（同日，实测驱动）**：初版把「CPU 异常的轮」直接判为整批不可用，
结果 `weaknet_p8` 第 1 轮 CPU 47.6%（其余 20~27%，上一档刚结束的余温）就让整批被判死，
而该轮吞吐 8,032 就在中位 8,007 旁边、整批 cv 仅 0.73%。现改为
**「CPU 异常 **且** 该轮吞吐偏离中位 >2%」才作废**，只异常不偏离的轮仍记在
`suspect_rounds` 里供追溯。判据频繁误报的后果是字段被整体忽略，护栏等于没有。

**两条已知限制（不做粉饰）**：

1. **MAD 的零点退化**：当超过一半样本完全相同（如 `[7946, 2459, 7946, 2918, 7946]`），
   MAD = 0，此时它无法表达离散度。这类分布由 `cv_pct` 兜住（36%），
   `suspect_rounds` 里也有 `mad == 0` 的专门分支。
2. **引擎与 iperf3 的覆盖区间天然不同**：引擎字节含 CONNECT 握手与重传、按墙钟计；
   iperf3 按剔除预热后的有效窗口计。所以正常值应**略微为正**（实测 +0~+2%），
   不能要求「越接近 0 越好」，更不能用 6 s 的窗口去除 10 s 的字节
   （试过，虚高 70%，已回退并写进代码注释）。

## 4.6 短样本超发的真实模型：时间额度（2026-11-14 修正）

**旧结论（错）**：1 MB 档超发 +25~29%，反推「**固定 0.42 MB 免费额度**」，
修正公式 `ratio = 1 + B/mb`。

**为什么错**：那批数据是「**固定速率、只变样本大小**」（1/2/4/8 MB）。在这个实验设计里，
「固定字节额度」和「固定时间额度」给出的 B 都是常数，**两者不可分辨**。要区分它们，
必须「固定大小、只变速率」。

**新实测**（Windows，进程内引擎，每档 3 次取中位，间隔 0.6 s 让桶重新攒满）：

| 场景 | 实测 kbps | 偏差 | 反推 B (MB) | B/速率 (MB per kbps) |
|---|---|---|---|---|
| 2000 kbps · 1 MB | 2,071 | +3.6% | 0.034 | 1.70e-5 |
| 4000 kbps · 1 MB | 4,407 | +10.2% | 0.092 | 2.30e-5 |
| 8000 kbps · 1 MB | 9,802 | +22.5% | 0.184 | 2.30e-5 |
| 16000 kbps · 1 MB | 25,460 | +59.1% | 0.372 | 2.33e-5 |
| 4000 kbps · 4 MB | 4,093 | +2.3% | 0.091 | 2.28e-5 |
| 8000 kbps · 4 MB | 8,382 | +4.8% | 0.182 | 2.28e-5 |
| 8000 kbps · 16 MB | 8,087 | +1.1% | 0.172 | 2.15e-5 |

B 随速率**线性增长**、B/速率恒定 → 是时间额度。把 B 折算回秒（`c = S×8/R − t`）：

| 场景 | 理想时长 | 实测 | 少花的时间 c |
|---|---|---|---|
| 2000 · 1 MB | 4.096 s | 3.955 s | 0.141 s |
| 4000 · 1 MB | 2.048 s | 1.859 s | 0.189 s |
| 8000 · 1 MB | 1.024 s | 0.836 s | 0.188 s |
| 16000 · 1 MB | 0.512 s | 0.322 s | 0.190 s |
| 4000 · 4 MB | 8.192 s | 8.006 s | 0.186 s |
| 8000 · 4 MB | 4.096 s | 3.909 s | 0.187 s |
| 8000 · 16 MB | 16.384 s | 16.208 s | 0.176 s |

即 `t ≈ S×8/R − 0.19 s`，六档落在 0.176~0.190 s；唯 2000 kbps·1 MB 档为 0.141 s。
0.19 s 比桶容量 0.25 s 少的那 0.06 s，来自 `consume()` 的睡眠取整与分块扣减
（每次 `asyncio.sleep` 实际会多睡几毫秒，块数越多累计越多）——**不要把它当成新常数**，
它是「块数 × 每次取整误差」的函数，换个块大小就会变。能当常数的只有 `BURST_SEC`。

**正确的修正公式**（替换旧的 `1 + B/mb`）：

```
超发比例 ≈ min(空闲时长, BURST_SEC) / 理想时长，理想时长 = S×8/R
```

**两端不一致（未修，需产品决策）**：Windows `Bucket.BURST_SEC = 0.25`，
Android `Pipe.Bucket` 原容量是 `rate`（1.0 s），2026-11-14 已对齐为
`rate × BURST_SEC = 0.25 s`（真机 A/B：短样本超发 1.463× → 1.014×）。
同一 1 MB / 8000 kbps 样本，Windows 理论上限 +24%，Android 理论上限 **+98%**。
`Bucket` 的类注释里明确写了「不能给到 1 秒：4 MB 下载会一口气吃掉整秒配额，
测出来变成两倍多」——**这条结论只落在 Windows 侧**，Android 仍是我行我素。
这与 §5「同一份配置在两端行为一致」的承诺直接冲突。

改动点（Android，各一处）：`Pipe.java` 的 `setKbps` 与 `refill` 里
`tokens > rate → tokens = rate` 改为 `rate * BURST_SEC`，并让构造函数初值同源。
**未改**：Android 只能真机量化，本轮无设备，且改桶容量会改变真实链路的突发容忍度，
需先 A/B。`tests/_t_spec_parity.py` 的 A11 已锁住「按时间计」这一语义，
并把两端的秒数差打在 PASS 行里，防止再被写成字节额度。

**采集侧建议**：任何 `< 1 s` 理想时长的样本都不该直接引用；要么预热丢弃前 0.3 s，
要么在结果里标注 `burst_credit_s`。

## 5. 明确不承诺的能力

- 不模拟链路层的 MTU 分片、PMTUD 失败、ECN、AQM（`tail-drop`/`RED`）行为。
- 不模拟中间设备（NAT 超时、代理劫持、运营商 QoS）。
- 不模拟真实丢包引发的拥塞控制差异（CUBIC/BBR 的反应曲线）。
- 不保证与 `tc netem` 在数值上等价，只保证**同一份配置在两端（Windows/Android）行为一致**。
